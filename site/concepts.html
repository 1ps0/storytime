Core Concepts

Everything in storytime builds on a few foundational ideas. This page defines them so the rest of the docs can reference without re-explaining.

Personas

Personas are domain-expert lenses, not characters. They don't role-play — they provide structured perspectives that ensure the plan considers all relevant dimensions of a problem.

Archetypes

ArchetypePerspectiveWhat they ask
OWNERWrote the code, knows where everything lives"This touches X, which depends on Y..."
OPERATORRuns it in prod, wants observability"What's the kill switch? How do I monitor this?"
DOMAINDeep expertise in the problem area"The standard approach for this is..."
SYSTEMSKnows the runtime, infra, failure modes"At scale, this will bottleneck at..."
PLATFORMKnows the product, users, business case"Users expect... The business needs..."
SKEPTICChallenges assumptions, asks hard questions"Do we actually need this? What if we don't?"

Every session has at least one OPERATOR. Minimum 3 personas, maximum 7.

Permanent Cohort vs Specialists

Cohort personas persist across sessions. They accumulate context, evolve their expertise, and remember past decisions. They live in specs/.storytime/cohort/.

Specialists are temporary — recruited for a specific problem, with an exit condition. When their contract completes, they can be promoted to the cohort or released.

Addressing Personas

You can talk to any persona at any time using @name or @role syntax:

@noa what do you think about adding WebSocket support?
@operator is this safe to deploy without a kill switch?
@skeptic do we actually need this?
@team what did we decide about the cache TTL?

This works in any conversation where a storytime cohort exists — no active session required.

Episodes and Threads

Sessions for the same topic are episodes of an ongoing story. Episode 1 is the cold start. Episode 2+ are warm starts that continue the narrative.

The thread (_thread.md) is the bookmark. It tracks:

  • Episode list with dates and phases completed
  • Current team roster
  • Open questions from the last phase
  • Last git commit (for drift detection)

Threads auto-checkpoint after every phase. If a session is interrupted, the next invocation detects the incomplete thread and offers to resume.

Warm Start

When you revisit a topic, storytime synthesizes a narrative preamble — a "previously on..." that reconstructs the story arc from living documents, persona histories, and git delta. The preamble is dynamic (never cached) and persisted as an audit trail.

Decisions

Decisions are append-only, numbered per topic (RATE-001, RATE-002). Each records:

  • What was decided and why
  • Which personas drove it
  • Code or doc citations grounding it
  • Status: accepted, superseded, or revisited

Decisions are never deleted, only superseded. The decision log is the institutional memory of the project.

Grounding and Citations

Every technical claim must be grounded — cited against evidence. Storytime uses a multi-source citation system:

SourceFormatWhen to use
Codesrc/auth.ts:32Claims about runtime behavior
Repo filesdocs/api-design.md:15Claims about project intent or conventions
Library docs[redis.io/commands/zrangebyscore]Claims about external system behavior
Gitcommit abc123Claims about what changed and when
StandardsRFC 6585 §4Claims about protocols or specs
Web[url]Benchmarks, blog posts, CVEs

Evidence hierarchy: Code > Git > Repo files > Library docs > Standards > Web. Personas should proactively research external claims via WebSearch/WebFetch.

Complexity and Scale

Complexity measures how hard (cognitive integration cost). Fibonacci scale:

LevelComplexityHuman analog
1Single-file, single-conceptQuick fix
2Few files, one systemStraightforward task
3Multiple files, one systemA morning's work
5Cross-system, multiple ownersSolid day of work
8Architectural, multi-systemMulti-day effort
13Foundational changeSprint-sized (MUST decompose)

Scale (1-5) measures blast radius, not complexity:

  • 1 (file) — a single file
  • 2 (module) — a module or repo
  • 3 (service cluster) — touches multiple services
  • 4 (users) — affects users directly
  • 5 (ecosystem) — crosses organizational boundaries

Complexity and Scale are orthogonal. Both are always stated with prose.

Phases

PhaseWhat happensOutput
SURVEYExplore codebase, scan artifacts, build mental modelsurvey.md + fingerprint

ICEBREAKERTeam discusses status quo, identifies sub-problemsicebreaker.md
BREAKOUTParallel deep dives on sub-problemsbreakout-*.md
PAUSEUser reviews breakout summaries before convergence(user direction)
CONVERGETeam merges findings into a planplan.md
REVIEWUser challenges, team defends or revises(inline)

Phases collapse when empty. Not every run uses every phase.

Modes

Conversation Modes

  • Inline (default) — user is present, can interject any time
  • Deliberation — "go figure this out" — team works autonomously, returns with findings
  • QA — @persona question — direct query, no session needed

Bootstrap Modes

  • Storytime-native — full .storytime/ structure
  • Adapt-in-place — work within the repo's existing doc conventions
  • Export-only — one-shot output, no persistent state

Automation Levels

  • Manual — user approves each phase transition
  • Guided (default) — phases run automatically, user reviews at pause + review
  • Auto — runs end-to-end, presents final plan
